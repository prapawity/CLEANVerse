# Developer storage discovery

Status: experimental read-only discovery, 2026-11-21. No deletion or whole-machine scan is implemented. The user selects the scan root and exclusions; scope, symlink and partial-result limitations remain those of the desktop scanner.

## Supported candidates

Within the chosen root, detect `node_modules` with a parent `package.json`, `target` with a parent `Cargo.toml`, `.dart_tool` with a parent `pubspec.yaml`, `.gradle` with a parent Gradle settings/build file, SwiftPM `.build` with `Package.swift`, CocoaPods `Pods` with `Podfile` or `Podfile.lock`, and Python `.pytest_cache`/`.mypy_cache` with a recognized project or tool marker in the parent. These patterns identify candidates, not proof that content is disposable. Show the marker and directory modification time; that time is not last use. Limit results to 200 and report overflow in skipped items. Preserve user data and never run tool commands or delete files automatically.

Sizes sum logical file lengths observed during traversal. They may be partial, can count hard links or nested candidates more than once, and do not measure physical storage or reclaimable bytes.

Results distinguish project folders identified by markers from tool storage candidates identified by location. During scanning, the UI shows the number of files found and, when content matching is enabled, the number of eligible files checked. These are observed counts, not an estimate of total scan duration or completion percentage. Cancelled and incomplete results remain explicitly labeled.

### Possible global caches

The scanner recognizes Gradle `caches` under `GRADLE_USER_HOME`, Cargo `registry/cache` under `CARGO_HOME`, the Dart package cache under `PUB_CACHE`, and npm `_cacache` under `npm_config_cache` / `NPM_CONFIG_CACHE`, or the documented platform defaults if no corresponding environment variable is set. On macOS it additionally identifies conventional Xcode `DerivedData`, `Archives`, `iOS DeviceSupport`, and CoreSimulator `Devices` locations as unverified candidates. Archives and simulator devices are not generic caches: they can contain unique release builds, symbols, app data and settings. These are detected only when the candidate directory is inside or is the selected root and is not excluded. Relative or invalid configured paths are skipped rather than silently replaced by a default. The label identifies whether the path came from an environment variable or a possible default; tool configuration files, Xcode preferences, command-line overrides, and child-process environments are not inspected, so a path is a candidate and may not be the active location. No tool commands are run. Global cache paths may contain valuable shared or manually modified data and must never be automatically deleted.

Additional candidates include the pip cache (`PIP_CACHE_DIR`, `XDG_CACHE_HOME` on supported non-Windows versions, or platform default) and Go module cache (`GOMODCACHE`, first `GOPATH` entry, or default). Go can also persist settings via `go env -w`, and pip configuration or version differences can change its effective cache location; neither is inspected here. Invalid nonempty overrides are not replaced by default paths. Go module caches may contain private source or be needed offline.

## Why cleanup needs a separate design

The current Developer Cleanup interface allows users to select discovered project folders and tool storage candidates and review an in-memory snapshot. Nothing is selected automatically. Review shows source, scope, observed logical sizes and possible impacts; Xcode archives and Simulator device data are flagged as potentially important, and all other candidates require review. These labels are not safety or ownership determinations. Selections are cleared when scan options, scope, or exclusions change. Moving to Trash is disabled, and no delete, restore, background cleanup, or persistent history capability exists.

Before enabling any removal, verify selection reset on rescans, exclusions and navigation; changed and replaced items; symlinks, junctions and hard links; shared caches and offline dependencies; denied permissions; running tools; and unavailable or partial Trash operations. Use temporary fixtures and verify native behavior separately on every supported OS. UI, accessibility, selection and removal behavior remain untested for this change at the owner's request.

Project dependency and build directories may contain local edits, unavailable packages or active build state. Deleting may break offline builds, require downloads and slow rebuilds. Gradle caches can be shared and concurrently locked; Cargo home also contains config and credentials and its internal structure is not stable. npm describes its cache as self-healing, so blanket cleanup is not always beneficial. Custom environment variables and tool configuration can move cache locations.

Before implementing removal, design an explicit allowlist per tool, identify ownership and active processes, validate identities and scope at operation time, distinguish Trash support and permanent operations, disclose downstream effects, and complete `SAFETY.md` release gates. Do not classify whole home directories or credentials as caches. Whole-machine discovery needs an explicit drive/scope picker, permissions, exclusions, filesystem boundaries and honest partial-results reporting.
